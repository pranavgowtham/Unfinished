# BUILD SPEC — "Unfinished"

Rebuild spec for a fresh Claude session on another machine. No source files are
transferred — this document contains everything needed to regenerate an
equivalent (or better) implementation from scratch: product thesis, exact
content schema, exact algorithms, visual language, and a build order.

Hand this whole file to Claude on the new machine as the first message, or
drop it in the repo root and say "build this."

---

## 1. Product thesis (read this first, it governs every decision below)

**Problem:** people doomscroll because the feed is never finished. Apps that
try to deliver "informative" content (Deepstash-style fact cards) fail
because every card *is* finished — complete, so nothing pulls the user
forward. Instagram's hook isn't visuals, it's that nothing ever resolves.

**Core idea:** stop publishing facts. Publish open questions. Content is
restructured into **threads** of 4–8 **beats**. Every beat closes the
question the previous beat opened and opens a new one — like a serialized
drama, not an encyclopedia entry.

**Three non-negotiable rules:**
1. Every screen ends mid-question. A screen that is fully self-contained is a
   bug, not a feature — reject and rewrite it.
2. The user can leave *anything*, instantly, at zero cost. Swipe sideways =
   leave. This is never blocked and never asks "are you sure." Bailing is
   treated as a signal (a downvote), never as a failure state to prevent.
3. The system visibly learns from taps/skips and *acts* on it — and tells the
   user why, every single screen. ("Why this: ...")

**Explicit non-goals:** no like/rate buttons (grading is homework — ask "what
do you think," not "was this good"), no streaks/badges/completion ceremony,
no gamification. The primary reaction is **"huh"** (surprise/curiosity).
A secondary reaction, **"ouch"** (behavioral self-recognition), exists but
must be capped at ~15% of content — overused it becomes accusatory and the
whole product mood collapses into guilt instead of curiosity. This was a
real mistake made and reversed in an earlier version (see §9).

**Real metric, for the record:** not time-on-app. Time spent *and* regret,
side by side — "did you feel it was worth it," asked once at session end.
Optimizing for engagement alone just rebuilds Instagram with better content.

## 2. The nine tension types (the taxonomy — this answers "what content belongs here")

Every beat is tagged with exactly one type:

| key | label | user feels |
|---|---|---|
| `curio` | curiosity gap | interesting |
| `counter` | counterintuitive | surprising |
| `mech` | hidden mechanism | revealing |
| `scale` | scale shock | awe |
| `pred` | prediction | a game |
| `mys` | mystery | a story |
| `diag` | diagnosis | confronted (capped ~15% of total feed) |

(Two more exist in the design doc but weren't implemented as distinct in the
prototype: `contradiction` and `stakes` — fold these in if you expand the
taxonomy later.)

Content pillars (topics), four in the working prototype:

- `money` — Money mechanics ⭐ strongest pillar: universally wanted, badly
  explained, every claim has a number (good for guess-then-reveal).
- `systems` — Hidden systems (airline pricing, retail layout, how the things
  around you actually work).
- `science` — How things work / numbers that break intuition.
- `behaviour` — Diagnosis content. Keep this one capped.

## 3. Content schema

### 3.1 Thread

A thread has four fields: an id (short slug, e.g. "pay"), a display name
(e.g. "Where Your ₹7 Went"), a topic (one of money, systems, science,
behaviour), and an ordered list of 4 to 8 beats.

### 3.2 Beat — six types

Every beat, regardless of type, carries a tension-type tag and a short
"loop" string (about five words, shown in the top-bar chip, summarizing the
open question the beat ends on).

**Text beat** — plain informative beat. Fields: the tension type, the loop
string, a body of copy, and an optional short sub-line. The copy uses the
kinetic text markup described in section 5.3: double-asterisks around a
word or phrase for emphasis, double-at-signs around a word for a "hold to
reveal evidence" trigger, and line breaks between sentences. Rendered with
a single "huh" reaction button at the bottom.

**Flinch beat** — the behavioural-diagnosis beat; this is where the
diagnosis tension type lives. Same shape as a text beat, but it renders an
"ouch" button instead of "huh," and clicking it queues a callback beat for
later use ("You flinched at this earlier. Still true?"). This type must
stay rare — it is the capped fifteen percent described in section 1.

**Call beat** — a guess-before-reveal multiple choice. Fields: the tension
type, loop string, the question text, a list of options (each with a label
and a flag for whether it is the correct option), a placeholder percentage
and a short label describing what that percentage represents, a reveal
line to show when the user picked wrong, a reveal line to show when the
user picked right, and two signal pairs — one logged when the user is
wrong, one logged when the user is right, each pair being a short headline
plus a longer detail sentence. The percentage is the share of past users
who took the wrong path named in the label; the animated bar always fills
to that percentage regardless of what the current user picks. On click:
lock every option, highlight the user's own pick as correct or incorrect,
also reveal the correct option if the user was wrong, animate the
percentage bar, show the matching reveal text, log the matching signal
pair, and increase the topic's weight.

**Chat beat** — the same guess-and-reveal mechanic as a call beat, staged
as a text-message exchange, used specifically for behaviour content.
Fields: everything a call beat has, plus who the other party is, their
opening message, and — for each option — a short reply line that other
party sends back after the user picks it. On click: show the user's own
chat bubble, a brief "typing" indicator, then the other party's reply
bubble, then the same percentage-bar-and-reveal sequence a call beat uses.

**Mechanism beat** — a beat whose supporting evidence is hidden behind a
tap. Fields: tension type, loop string, the main copy (containing the
hold-to-reveal trigger word), the evidence paragraph itself, a short
citation or sourcing note, and an optional signal pair. It renders the
copy together with a visible "not convinced? press '<word>'" button. On
click — or on clicking the highlighted trigger word inline — reveal the
evidence paragraph and its sourcing note, raise the evidence-need and
depth-preference axes of the user model, raise the topic weight, and log
the signal if one is defined.

**Poll beat** — a zero-commitment standalone poll, not attached to any
thread; this is also the type used for the "standalone" filler share of
the feed. Fields: tension type, topic, the question text, a list of
options each carrying a label and a percentage (the full set sums to
roughly one hundred), and a reveal line shown once answered. On click:
lock all options, reveal every option's percentage as an animated bar
with the user's own pick highlighted, show the reveal line, log a signal,
and apply a small topic-weight increase.

### 3.3 One-offs (standalones, no thread)

A one-off is the simplest unit: a tension type, a topic, and a single
piece of kinetic-text copy. It renders with only a "huh" button — no
question, no reveal, nothing to finish.

### 3.4 Signals

Every interaction that teaches the user model logs a signal: a short
headline and a longer detail sentence, with an optional "bail" marker used
specifically for signals generated by leaving a thread early. Signals are
shown in a running list in the UI ("Signals captured"), newest entry at
the bottom, and are deduplicated by headline — the same exact headline is
never logged twice in one session.

## 4. Interaction rules

- **Swipe up / "next" button / spacebar / down-arrow** → advance one beat.
  Always available, never blocked, never requires completing the current
  beat first.
- **Swipe sideways / "something else" button / right-arrow** → leave the
  current thread immediately, go elsewhere. Zero cost, zero confirmation.
- **Tap** → the optional stuff (answering a call/poll/chat, holding for
  evidence, tapping specific lines).
- Nothing is ever mandatory. Skipping past an unanswered call/poll is valid
  and simply yields no signal.
- No like/rate button exists anywhere in the UI, by design.

Feed composition target (approximate, used to weight the scheduler — see §5):

| share | unit kind |
|---|---|
| ~55% | next beat of a live (in-progress) thread |
| ~20% | opener for a brand-new thread |
| ~15% | standalone (poll or one-off fact, no thread) |
| ~10% | callback (resolving a flinch from earlier) |

## 5. The user model and scheduler (this is the part that must survive the rebuild byte-for-byte in behavior, not just in spirit)

### 5.1 State

The running state consists of: a weight between 0 and 1 for each of the
four topics (money, systems, science, behaviour), all starting at 0.5; two
further axes, depth preference and evidence need, starting at 0.5 and 0.3
respectively — depth runs from "wants tactics" at 0 to "wants mechanism"
at 1, evidence need runs from "takes the claim" at 0 to "show me proof" at
1; a per-thread record of how many beats have been shown and whether the
thread is new, live, done, or abandoned; the id of the last thread shown;
the kind of the last unit shown; the running signal list with its
dedupe set; and a small queue of pending callback texts.

### 5.2 Topic weight update — "bump" (zero-sum attention)

Interest is relative, not absolute. If topics could only climb, an engaged
user would saturate all four at the maximum and the scheduler would have
nothing left to discriminate on. So any positive increase to one topic's
weight is paid for by a small decrease spread across the other three.

Precisely: when a topic receives a positive or negative amount, that
topic's weight is adjusted by that amount and clamped back into the range
0.03 to 1.0. If the amount was positive, divide it evenly across the other
three topics, multiply each share by 0.7, and subtract that from each of
the other three topics' weights (also clamped to the same 0.03–1.0 range).
A negative amount — used only when a user abandons a thread — is applied
only to that one topic, with no corresponding increase elsewhere.

Magnitudes used by each interaction, so the feel of the rebuild matches
the reference: tapping "huh" on a text beat raises that topic by 0.14 (a
one-off standalone's "huh" raises it by 0.12); answering a call, chat, or
poll beat raises the topic by 0.16 for a call and 0.14 for a chat;
revealing a mechanism beat's evidence raises the topic by 0.10 and
additionally raises the evidence-need axis by 0.22 and the depth axis by
0.12; answering a poll beat inside a thread raises the topic by 0.10;
abandoning a live thread lowers that topic by 0.18. The depth and
evidence-need axes themselves have no decay — they only move when a
mechanism beat's evidence is revealed.

### 5.3 Kinetic text markup (shared by every renderer)

A tiny inline markup is parsed before each beat is painted. Text wrapped in
double asterisks becomes an emphasized span in the accent color. Text
wrapped in double at-signs becomes a "hold" span — underlined and
clickable, and clicking it triggers the mechanism-beat evidence reveal if
one is present on the current beat. Line breaks in the source copy become
line breaks on screen. Beyond that markup, every individual word in the
copy is wrapped in its own span and given a staggered fade-and-rise-in
entrance animation, with each successive word's delay increasing by about
a twentieth of a second, so the text visibly "types in" word by word on
every new screen. This is the "kinetic text" effect and it is priority one
of the presentation layer — its job is to pace reading for a user with low
energy, the same job a TikTok auto-caption does.

### 5.4 Candidate scoring

To build the ranked candidate list: take every thread that is currently
live and still has beats remaining, followed by every thread that hasn't
been started yet. For each one, start with its topic's current weight as
the base score, then add a boost of 0.22 if the thread is live, and add a
further boost of 0.30 if it is the thread the user was just on. Sort the
full list by that score, descending. The top four of this list are what
the "Next up — and why" panel displays live.

The boost for the thread the user was just on is deliberate: it creates
"stickiness," so a thread the user just engaged with is very likely —
though not certain, since the scheduler's randomness below can still
interrupt it — to be the one that continues.

### 5.5 Scheduler — picks the next unit kind

The scheduler runs on every advance, with an optional "away" mode when the
user has just swiped sideways to leave. There are four possible outcomes:
continue a live thread, open a new thread, serve a standalone (a poll or
a one-off fact, alternating so that roughly every third standalone is a
poll), or serve a callback.

If the user just swiped away: take the candidate list, remove the thread
they were just on, and if anything remains, serve the top of that list
(continuing it if it was already live, opening it if new), with the
reason "You left the last one. Switching topic — [that topic's label] is
your next highest weight." If nothing remains, serve a standalone with the
reason "Nothing queued that fits. Serving a standalone."

Otherwise — a normal forward advance — first check for momentum: if the
user is currently mid-way through a live thread with beats still
remaining, and the previous unit shown was not itself a standalone, there
is a 58% chance of simply continuing that same thread, with the reason
"You engaged with the last beat, so the thread continues. Something is
still unresolved in it."

If momentum doesn't apply, roll again: if there is a pending callback and
this second roll lands above the 91st percentile, serve the callback with
the reason "Bringing back something you committed to earlier." Otherwise,
if the previous unit wasn't already a standalone and this roll lands above
the 74th percentile, serve a standalone with the reason "A standalone — no
thread, nothing to finish. This is about fifteen percent of the feed on
purpose."

Failing all of the above, fall through to the top of the candidate list:
serve it (continuing if live, opening if new) with the reason "[topic
label] is your highest weight ([weight as a percentage])," followed by
either ", and you left this thread unresolved" if it was already live or
", so a new thread from it" if it's new. If the candidate list is
completely empty, serve a standalone with the reason "Threads exhausted in
this demo. The real product keeps generating."

### 5.6 Advance / state transition on each step

On every step, before picking the next unit: if the user was on a thread
beat and is now leaving it sideways while it isn't finished, mark that
thread abandoned, lower its topic weight by 0.18 as described in section
5.2, and log a bail signal with headline "Left '[thread name]' at beat
[n]" and detail "[topic] weight dropped to [new weight]. Bailing is a
downvote we never had to ask for." If instead the thread had simply run
out of beats, mark it done — silently, with no ceremony shown to the user.

Then run the scheduler from section 5.5. If it chose to continue or open a
thread, mark that thread live, take its next beat, advance its beat
counter, and record it as the last thread shown. If it chose a standalone,
clear the last-thread record. If it chose a callback, pop the next
pending callback text off the queue.

Finally, attach the scheduler's reason string as the "Why this" line,
prefixing it with any note left over from the previous interaction (for
example, "You marked the last one interesting, so this topic got
heavier"), and render the new beat — sliding up for a normal advance,
sliding sideways for a "leave" action.

The "why this" string is the single most important UI element for
differentiating this from a black-box feed — it must be regenerated and
shown on literally every screen, never skipped.

## 6. Rendering spec (what the user actually sees, screen by screen)

Phone-shaped single-column layout (mobile demo chrome), four fixed regions
top to bottom:

1. **Top bar** — logo, a "N live" chip (count of in-progress threads), a
   "loop" chip showing the current beat's short open-question string.
2. **Meta strip** — tension-type label (color-coded per type, see §7) +
   the "Why this: ..." line. Toggleable for demo purposes.
3. **Stage** — the actual beat content, full remaining height, scrollable.
   New beat replaces old with a slide/fade transition: slide-up for normal
   advance, slide-sideways for "leave" transitions.
4. **Bottom nav** — two buttons, "next ↑" and "something else →", plus a
   static hint line ("next always works · nothing required · leave
   anything, free").

A side panel (desktop-only companion, hide on narrow viewports or make it a
drawer on mobile) shows the live internals, deliberately exposed as a
teaching/demo device:
- **Your model** — one bar per topic weight + the depth and evidence-need
  axes, all labelled with human phrasing, not raw numbers only.
- **Next up — and why** — top 4 scored candidates with their reasoning.
- **Signals captured** — running log, newest at bottom.
- **Demo controls** — toggle the why-this strip, restart, keyboard hint
  (`↓`/`space` = next, `→` = leave), and a visible disclaimer that all
  figures are placeholders pending real citations.

Gesture support: swipe up/down via touch, left/right via touch; arrow keys
and spacebar as desktop equivalents.

Error handling: wrap the per-step render in a try/catch that renders the
error inline on the phone screen instead of leaving a blank stage — a
content/data typo should never produce a silent dead end during a live demo.

## 7. Visual language (replicate the mood, exact hex optional)

Dark, editorial, slightly moody — not flat corporate SaaS, not neon gamer:

- Background: near-black with a very subtle radial vignette lightening
  toward the top (`#07070a` base, lightening to `#16161f` near top-center).
- Card/surface colors: `#131319` (primary surface), `#1b1b24` (raised
  surface e.g. buttons/pills).
- Ink/text: off-white `#f4f2ef`, muted secondary text `#8b8b99`, dim tertiary
  `#5a5a67`, hairline borders `#282834`.
- Accent palette, one hue per tension type, used consistently everywhere
  that type appears (label color, left-border accents):
  - accent/coral `#ff6b5a` — diagnosis
  - gold `#ffd166` — hot/highlight chip, counterintuitive
  - green `#5ad1a0` — mechanism, "right" answers
  - blue `#7aa2ff` — curiosity gap
  - purple `#b98cff` — scale shock
  - orange `#ff9f6b` — prediction
  - teal `#7fe0d4` — mystery
- Body copy font: serif (Georgia/Times) at ~24px/1.4 line-height — this is
  deliberate, it reads as "editorial/considered" rather than app-UI. All
  chrome/UI text (buttons, labels, panel text) uses the system sans-serif
  stack instead, to visually separate "the knowledge" from "the interface."
- Buttons/pills: fully rounded, subtle 1px border, barely-there hover lift.
- Percentage bars: horizontal track, animated width fill (CSS transition,
  ~1.1s cubic-bezier ease), label left-aligned inside the bar, value
  right-aligned.
- Word-by-word fade-up entrance for all kinetic text (see §5.3).

None of this is sacred — a rebuild on a different design system should keep
the *functional* intent (serif-for-knowledge vs sans-for-chrome, one hue per
tension type, animated reveal bars, zero completion ceremony) rather than
copying pixel values.

## 8. What is real vs. hand-authored in the reference prototype

Be honest about this when rebuilding or demoing — it's a stated product
position, not just a caveat:

| Genuinely working logic (reimplement exactly) | Hand-authored placeholder (replace, don't copy) |
|---|---|
| Scheduler (`candidates`/`schedule`/`advance`) | The 5 threads' actual copy/beats |
| Topic-weight model incl. zero-sum decay (`bump`) | The 8 one-off facts |
| "Why this" string generation | The 3 standalone polls |
| Bail = real downvote signal | All percentages (64%, 71%, 58%, 76%, fuel-share, gold-cube, brain-energy, etc.) — every single one is invented and must get a real citation before any external use |
| Live queue reordering | — |

No AI call, no server, no persistence exists in the reference prototype —
state resets on reload. That's an acceptable prototype limitation; it is
**not** acceptable in the real product (see §9, item 2).

## 9. Known open work (carry forward, don't silently drop)

In priority order, as of last working session (2026-09-26):

1. **Replace every placeholder statistic with a real cited source.**
   "Informative content" is the entire product promise — a wrong number on
   stage or in production sinks the premise. Nothing in §3's example content
   should ship externally until each percentage/claim has a citation.
2. **Build the thread generator.** Source document in → validated beat chain
   out. Two mandatory quality gates, enforced in code, not by hand-checking:
   - **Open-ended check:** does every beat genuinely leave something
     unresolved? (A self-contained beat is a defect — reject and regenerate.)
   - **Citation check:** does every claim carry a real source? (Refuse to
     emit a beat with no citation — this is the generator's hard constraint,
     not a nice-to-have.)
   This is the single piece that answers "isn't this just a ChatGPT
   wrapper?" — everything else in this spec is UI/UX around it.

Earlier design mistake worth remembering so it isn't repeated: an initial
version made every beat behavioral-diagnosis content. It was accusatory,
narrow (excluded money/systems/science), and one-note. Fixed by introducing
the 9-type taxonomy (§2) and capping diagnosis at ~15%, with "huh" (not
"ouch") as the primary reaction. Don't regress on this.

## 10. Suggested rebuild order

Target stack is unspecified on purpose — pick whatever the new machine's
Claude setup is comfortable with (plain HTML/JS is sufficient to reproduce
the reference prototype 1:1; React/Vue/etc. fine for a production build).

1. **Data layer** — implement the schema in §3 as plain data (JSON/objects).
   Port or re-author the 5 example threads + 8 one-offs + 3 polls from §3/§9
   as placeholder content, clearly marked as such.
2. **Model + scheduler** — implement §5 exactly (the bump rule, candidate
   scoring, the scheduler, and the advance step) as pure, testable logic
   decoupled from rendering. This is the part that must behave identically
   to the reference, so follow the exact numbers and rules in §5.2–5.6
   directly rather than improvising.
3. **Renderers** — one render function per beat type (§3.2) plus kinetic
   text (§5.3). Wire up signal logging (§3.4) and the "why this" display.
4. **Shell UI** — top bar / meta strip / stage / bottom nav + side panel
   (§6), gestures (touch + keyboard), visual language (§7).
5. **Demo polish** — restart control, why-this toggle, error-boundary around
   the step function.
6. **Only after the above works:** start on the real thread generator
   (§9 item 2) — this is the actual hard, differentiating part of the
   product and should not be mistaken for "done" just because the UI feels
   polished.

## 11. One paragraph to hand to anyone, including a fresh Claude session, who needs the whole idea in one breath

> People doomscroll because Instagram is never finished. Learning apps fail
> because every card *is* finished — you read it, it's done, nothing pulls
> you forward. So we rebuilt informative content as an endless feed of
> interleaved serials: every screen ends mid-question about something you
> actually want to know — where the other ₹7 of your coffee went, which seat
> on a plane survives, why the milk is at the back — and you guess before we
> reveal. You can leave anything instantly, like Instagram. The difference
> is we tell you why you're seeing every single thing, and the figures are
> placeholders until every one of them has a real citation.
